# Feng Sync 改进方案（整体对标 FreeFileSync）

## 1. 目标与结论

Feng Sync 当前已具备可运行的同步内核：本地目录扫描、双向/镜像/更新规划、差异预览、冲突裁决、临时文件提交、双向基线、基础 Profile 持久化、批处理，以及 SFTP/Google Drive 的 rclone 接入雏形。现有 40 项自动化测试全部通过。

但产品仍处在“同步内核原型”阶段，与 FreeFileSync 的成熟桌面体验相比，主要差距不是再增加一个同步按钮，而是补齐完整的配置模型、清晰的设置归属、可靠的异常恢复，以及可解释、可追踪、可复用的工作流。尤其需要优先重做 Profile 设置和程序设置。

建议目标分三层：

1. **先可信**：消除可能导致误删、基线错误、设置丢失、远端双向同步错误的风险。
2. **再完整**：形成与 FreeFileSync 类似的“比较设置 + 过滤器 + 同步设置 + 执行后动作”的 Profile 配置体系。
3. **后高效**：增加批处理、计划任务、日志与故障恢复，支持长期无人值守运行。（实时监控功能已移除，参见 §11）

## 2. 当前能力与差距

| 双向同步 | 本地可用 | 远端没有持久化基线，却仍允许双向模式，可能把冲突判断成首次同步 | P0 |
| 镜像/更新 | 基本可用 | 缺少执行前风险阈值、删除数量保护与空间检查 | P0 |

| 计划任务/命令行 | 缺失 | 已导出的 batch JSON 没有正式 CLI/任务计划程序入口 | P1 |
| 国际化/无障碍 | 缺失 | 中英文混用，emoji 图标依赖字体，键盘与屏幕阅读器支持不足 | P2 |

## 3. P0：首先消除的高风险问题

### 3.1 修正配置归属和 Profile 数据模型

当前 `ApplyProfile()` 会把 Profile 的并发数、校验、过滤器和版本策略写入全局 `_settings`；保存时又从 `_settings` 回写 Profile。这导致切换 Profile 会悄悄改变程序设置，也无法判断某项设置究竟属于全局默认值还是当前任务。

建议拆分为：

- `ApplicationSettings`：语言、主题、自动更新、日志保留期、默认并发上限、托盘行为、通知、默认错误策略、rclone 路径、遥测开关等全局值。
- `SyncProfile`：端点对、比较方式、同步方向、过滤器、删除/版本策略、校验、并发覆盖值、重试策略、完成动作、计划任务等任务值。
- `EffectiveProfileSettings`：运行时把 Profile 的 nullable override 与全局默认值合并，禁止 UI 直接改全局对象。

同时给配置文件增加 `SchemaVersion`、迁移器、校验器和损坏文件备份。保存继续采用临时文件原子替换，但要捕获并显示具体错误；加载失败不能静默恢复为空配置。

### 3.2 禁止不安全的远端双向同步

`BuildPlanAsync()` 仅在左右均为本地端点时加载双向基线；远端批处理也始终传入空基线。因此远端双向模式目前不具备可靠的删除传播和冲突检测语义。

短期措施：只要任一端是远端，双向模式明确禁用并解释原因。长期措施：将基线保存到本机应用数据，以稳定的端点身份 + 根目录组成键；保存双方文件 ID、大小、时间、hash 与能力信息，并为端点重命名、断连、认证更新提供迁移机制。只有基线完整且端点身份一致时才允许传播删除。

### 3.3 完成或隐藏“半实现”选项

- `Custom` 必须提供逐类动作矩阵：仅左存在、仅右存在、左更新、右更新、两边更新、删除/修改冲突分别选择复制、删除、忽略或冲突；完成前从 UI 隐藏。
- `RecycleBin` 必须使用 Windows Shell/适配器实现回收站；远端不支持时应禁用，而不是永久删除。
- `KeepDays` 必须真正执行版本清理，并提供最大版本数/最大总容量选项。
- `VerifyCopies` 本地改为可选 hash 校验，远端使用端点支持的 hash；若端点不支持，显示“仅大小校验”，不能标为完整校验。

### 3.4 加入删除和覆盖安全门

在执行前增加二次摘要：新增、更新、删除、冲突、总字节数、不可执行项。以下情况必须醒目确认，批处理则按策略中止：

- 首次运行镜像且将发生删除；
- 删除数量或比例超过 Profile 阈值；
- 源端为空、离线或扫描数量相对上次骤降；
- 目标空间不足；
- 归档目录位于被同步树内，或左右端点互相包含；
- 路径大小写、非法字符、文件/目录同名冲突；
- 计划生成后文件发生变化。

执行前保存不可变计划快照；复制完成后再删除；只有全部选中操作成功后才提交双向基线。部分成功必须保留旧基线或提交逐项事务状态，不能把失败项误记为已同步。

## 4. 用户使用体验改进

### 4.1 重构主流程

主界面保持 FreeFileSync 式的“配置列表—左右端点—比较结果—同步”心智模型，但减少歧义：

- 顶部主按钮固定为“比较”和“同步”，模式按钮打开当前 Profile 的“同步设置”，齿轮只打开“程序设置”。
- 路径输入支持历史记录、拖放、环境变量、收藏夹、最近位置、连接测试与空闲空间显示。
- Profile 列表支持重命名、复制、分组、搜索、排序、启停、最近运行状态和未保存标记；切换有未保存更改时提示保存/放弃/取消。
- 比较结果按“仅左、仅右、更新、删除、冲突、错误、相同”过滤，支持全选/反选、批量改方向、按路径搜索、展开目录层级。
- 使用清晰图标加文字，不只依靠颜色或箭头；所有动作提供 tooltip、键盘快捷键和可访问名称。
- 同步结束展示成功、跳过、失败、耗时、传输量和日志入口，不把“所有异步任务结束”简单等同“全部成功”。

### 4.2 提升响应性和可取消性

- 扫描、hash、比较、连接测试和加载 Profile 均提供进度与取消。
- 防止比较或同步期间重复点击、切换 Profile、修改端点或关闭窗口导致状态竞态。
- 大目录使用增量加载/虚拟化，避免一次性建立全部 `ComparisonRow`。
- 进度按字节统计，展示当前文件、总进度、速度、剩余时间、错误数；目前的“文件/秒”和模拟图不能代表真实传输性能。
- 关闭进度窗口不等同取消任务；提供明确的“后台运行”“取消”“暂停（能力允许时）”。

### 4.3 统一文案和反馈

把 `Profile`、`Relative path`、`Browse` 等中英文混用统一为可本地化资源。错误信息要包含：发生了什么、影响哪些文件、建议怎么处理、日志在哪里。状态栏只做摘要，详细错误使用可复制、可展开的错误面板。

## 5. 新功能方案

### 5.1 Profile 设置中心（最高优先级）

新增独立对话框，左侧导航、右侧配置页：

1. **常规**：名称、描述、标签、启用状态、颜色、端点对、交换端点。
2. **比较**：时间和大小、文件内容、仅大小、hash 策略、时间偏差容忍、符号链接、大小写敏感、隐藏/系统文件。
3. **过滤器**：包含/排除规则；按大小、日期、扩展名；规则测试器；预设和临时过滤器。
4. **同步**：双向、镜像、更新、自定义动作矩阵；移动/重命名检测；删除传播；冲突策略。
5. **版本管理**：永久删除、回收站、版本目录；时间戳/替换命名；保留天数、数量、容量；清理预览。
6. **性能与可靠性**：并发数、重试次数、退避、超时、hash 校验、失败后继续、限速、磁盘并发。
7. **自动化**：计划、启动时运行、静默模式、确认策略、成功/警告/失败后的动作。
8. **完成动作**：通知、打开日志、运行命令、关机/睡眠（需明确授权），以及命令参数预览。

对话框需支持“恢复全局默认值”“保存为默认值”“复制其他 Profile 设置”，每项标记其来源（全局默认或当前 Profile 覆盖）。

### 5.2 程序设置中心

新增正式设置窗口：

- **常规**：启动行为、最后 Profile、自动保存、确认提示、语言、主题、字体缩放。
- **默认值**：新建 Profile 的默认比较/同步/过滤/版本/并发设置，不反向修改既有 Profile。
- **日志与通知**：日志目录、格式、保留天数/数量、桌面通知、声音、敏感路径脱敏。
- **连接与性能**：全局任务并发上限、代理、限速、超时、重试、rclone 路径与版本检测。
- **集成**：Windows 右键菜单、开机启动、托盘、计划任务、文件关联。
- **维护**：配置目录、导入/导出全部设置、清理缓存/孤儿临时文件、诊断包、恢复默认值。

设置写入应异步、原子化、带版本迁移；敏感信息使用 Windows Credential Manager/DPAPI，不写入 Profile JSON 或日志。

### 5.3 自动化与批处理

- 增加正式 CLI：`fengsync compare/run --profile <id|file> --non-interactive --json-log`，定义退出码。
- 提供 Windows Task Scheduler 创建向导，而不是只导出 JSON。
- 将 `RealtimeMonitor` 接入 Profile，提供 debounce、冷却期、运行中变更队列、网络恢复重试与循环触发抑制。（该功能已移除，参见 §11）
- 批处理提供全局 Profile 并发限制、逐 Profile 结果、失败隔离、停止/继续策略和汇总退出码。
- 支持 Profile 链：按顺序运行、依赖成功才继续，避免当前无上限的 `Task.WhenAll` 争抢磁盘和网络。

### 5.4 比较、同步和恢复能力

- 可选内容比较、hash 缓存和时间戳容差。
- 稳定 ID 可用时进行移动/重命名检测，减少重复传输。
- 锁定文件/VSS 策略、长路径、符号链接、ACL/ADS/时间戳保留策略。
- 冲突批量规则和“保留双方并重命名”。
- 完整运行历史、结构化日志、失败项重试、孤儿 `.partial` 清理、崩溃恢复向导。
- 日志导出为 JSON/CSV/文本，支持按 Profile、日期、结果筛选。

### 5.5 内置 SFTP 服务器（局域网传输）

Feng Sync 应可选地作为轻量 SFTP 服务器运行，让局域网内其他电脑、手机或 NAS 直接访问指定目录。该功能属于**程序级服务**，在“程序设置 → SFTP 服务器”中配置，不绑定某个同步 Profile；Profile 仍可把本机共享目录作为普通端点使用。

#### 配置与交互

- 总开关：启用内置 SFTP 服务器。
- 启动策略：Feng Sync 启动时自动运行；可选“最小化到托盘后继续运行”。若用户要求未登录 Windows 也提供服务，应另行创建 Windows Service，不能依赖桌面进程。
- 监听配置：端口（默认建议使用非特权端口，如 `2222`）、绑定地址（默认“仅局域网接口”，另提供“仅本机”和明确警告的“所有接口”）。
- 服务状态：正在运行/已停止/启动失败、实际监听地址、端口、在线会话数、启动时间；提供启动、停止、重启、复制连接地址和测试连接按钮。
- 账号管理：用户名、启用状态、认证方式、可访问根目录、只读/读写权限。支持多个账号，禁止重复用户名。
- 认证方式：优先支持 SSH 公钥；可选密码。密码只允许设置/重置，不回显明文，并显示密码强度。
- 目录权限：每个账号限制在配置的虚拟根目录内，可选多个共享映射；必须阻止 `..`、链接跳转、大小写绕过和 junction/symlink 逃逸。
- 连接信息：展示 `sftp://<局域网IP>:<端口>/`、服务器主机密钥指纹及二维码，方便手机端配置。
- 日志：记录启动/停止、登录成功/失败、来源 IP、上传/下载/删除和错误；默认不记录密码及文件内容，可设置保留期。

#### 安全设计

- 首次启用时生成并安全保存独立 SSH 主机密钥，后续启动保持指纹稳定；提供查看、导出公钥和显式轮换功能。主机私钥使用 Windows DPAPI 或受 ACL 保护的密钥文件保存。
- 密码使用强 KDF（如 Argon2id/PBKDF2）保存盐化摘要，绝不写入 `FengSync.local.json`、Profile 或日志；更推荐存入 Windows Credential Manager/DPAPI 密文存储。
- 默认不开放匿名访问，不允许空密码，不支持明文 FTP，不默认暴露到公网或自动配置路由器端口映射。
- 限制连续登录失败次数并采用退避/临时封禁；提供最大连接数、单用户连接数、空闲超时、上传文件大小和带宽限制。
- Windows 防火墙规则必须由用户明确授权创建，界面显示规则状态并支持撤销；关闭功能不应遗留无主规则。
- 写入采用同目录临时文件后原子重命名，避免客户端中断留下完整名称的半文件；孤儿临时文件纳入维护清理。
- 对删除、覆盖、重命名、创建目录分别做授权；只读账号在协议层拒绝所有修改命令。
- 服务端异常不得拖垮同步任务或主 UI，监听器、会话和文件操作都要支持取消、超时与资源上限。

#### 与同步引擎的并发关系

当 SFTP 客户端正在写入某文件时，比较器不应扫描或同步该未完成文件；上传使用 Feng Sync 专用临时后缀并由扫描器统一排除。同步引擎与 SFTP 服务同时修改同一路径时，应通过共享的路径级锁或文件租约协调，并将“文件正在由 SFTP 会话写入”显示为可重试状态。（注：实时监控 debounce 已随功能移除一并删除）

建议引入以下组件：

- `SftpServerHostedService`：服务生命周期、监听和优雅停止；
- `SftpServerSettingsStore`：非敏感配置及 schema 迁移；
- `SecretStore`：账号密码摘要/密钥安全存储；
- `ShareAuthorizationService`：虚拟路径解析、根目录隔离和读写授权；
- `TransferLeaseManager`：与同步执行器共享的路径租约；
- `SftpAuditLog`：结构化审计记录与保留策略。

实现时应优先采用维护活跃、许可证兼容、支持现代 SSH 算法的 .NET SSH/SFTP 服务端库，并固定依赖版本、跟踪安全公告。若所选库只提供客户端能力，则不可用客户端库拼装不完整服务端。

#### 验收标准

- 重启 Feng Sync 后，自动运行设置生效，主机密钥指纹保持不变，密码不可从配置文件还原为明文。
- Windows、Android/iOS 和常见 NAS/命令行 SFTP 客户端可完成登录、列表、上传、下载、续传、重命名与删除。
- 只读账号无法通过普通路径、`..`、大小写、符号链接或 junction 写入/越出共享根目录。
- 端口占用、目录不可访问、密钥损坏和防火墙未放行都有明确诊断，不影响 Feng Sync 主程序启动。
- 上传中断不产生可被同步器当成完整文件的目标；服务停止时会话被优雅关闭，已提交文件不损坏。
- SFTP 传输与同步任务并发运行时无半文件同步、死锁或无界资源占用。
- 未启用服务时不监听任何端口；选择“仅本机”时其他局域网设备无法连接。

### 5.6 S3 对象存储与可扩展云端体系

Feng Sync 应新增 AWS S3 和 S3 兼容对象存储端点，并把当前写死的 `Local/Sftp/GoogleDrive` 分支重构为可扩展端点 provider 体系。首批兼容目标包括 AWS S3、Cloudflare R2、MinIO、Backblaze B2 S3 API 和用户自定义 S3 endpoint；后续可按同一机制增加 Azure Blob、OneDrive、WebDAV 等端点。

#### Profile 界面

- “添加云端端点”改为 provider 卡片选择页：Google Drive、SFTP、Amazon S3、S3 兼容存储。
- S3 字段包括显示名称、预设、Endpoint URL、Region、Bucket、根前缀、Access Key ID、Secret Access Key 和可选 Session Token。
- 高级项包括 path-style、TLS 信任、SSE-S3/SSE-KMS、storage class、分段阈值、part 大小、请求并发、超时与限速。
- 提供测试连接和浏览 Bucket，并区分 DNS/TLS、认证、Region、Bucket、权限、限流和时钟偏差错误。
- 凭据支持 Windows 凭据库、仅本次会话、环境/实例角色；Profile 只保存凭据引用。
- 显示端点能力摘要：hash、版本控制、服务端复制、原子移动、空目录、修改时间精度。

#### 对象存储语义

- 目录是 key 前缀；空目录默认不存在，可选使用目录标记对象。
- 重命名通常是复制后删除，不保证原子性，必须记录两个执行阶段。
- ETag 不总等于 MD5，分段上传或加密对象不能用 ETag 冒充内容 hash。
- 删除可使用普通删除或 S3 Versioning/delete marker；未启用 bucket versioning 时不得承诺可恢复。
- Glacier/Deep Archive 对象可能需要先恢复，应返回“等待恢复”状态。
- 大文件使用 multipart upload，并把 upload ID 与 part 状态写入 journal，以便继续或清理。

#### 架构与安全

- 新增 `IEndpointProvider` 与 `EndpointProviderRegistry`，UI 和主窗口不再按协议写死分支。
- 新增 `S3EndpointProvider`/`S3Endpoint`，负责设置、扫描、传输、删除、metadata 与能力探测。
- 扩展 `EndpointCapabilities`，表达服务端复制、内容 hash、版本控制、对象恢复和移动原子性。
- 统一 `CredentialReference`/`SecretStore`，禁止 secret、token 和 KMS 信息进入 Profile、日志或命令行。
- 默认强制 HTTPS；自签名证书只能显式信任指纹，不提供全局忽略 TLS。
- 按 list/get/put/delete 分别探测最小权限；缺少 delete 权限时禁止镜像模式。
- 执行前提示大量 API 请求、跨区域流量和归档恢复成本；支持指数退避、`Retry-After` 和请求幂等。

首期可继续使用 rclone 作为后端，但配置模型、凭据引用、能力探测和错误模型必须归 Feng Sync 所有，不能把 rclone remote 名称当作业务模型。未来可替换为原生 S3 SDK，而不改变 UI 和 Profile schema。

#### 验收标准

- AWS S3、MinIO 及至少两个 S3 兼容服务通过端点契约测试。
- 支持列表、上传、下载、覆盖、删除、根前缀和大文件分段上传。
- multipart/SSE 对象的 ETag 不会被误判为 MD5。
- 网络中断后可继续或清理未完成分段上传。
- S3 Versioning 未启用时不宣称删除可恢复。
- 凭据不出现在 Profile JSON、日志、进程参数或诊断包中。

## 6. Bug 消除清单

### P0

1. 修复远端双向无基线问题；未完成前禁用该组合。
2. `EndpointExecutor` 没有使用 Profile 的 `VerifyCopies`，也没有 journal；统一执行器语义。
3. `RecycleBin` 当前走永久删除路径；完成实现前禁止选择。
4. `Custom` 不是真正自定义；完成动作矩阵前移除入口。
5. `SyncPlan.CanExecute` 会因为任意未选中的冲突而禁止执行，且 Blocked/Conflict 与选择状态语义混杂；明确“全局阻断”与“可跳过冲突”策略并测试。
6. 比较后到执行前没有重新验证文件指纹，存在计划过期覆盖风险。
7. Profile 切换会污染全局设置，且未保存编辑可被无提示覆盖。
8. `LoadSettings()` 吞掉所有异常，损坏配置无提示；应备份损坏文件并进入修复流程。
9. 版本归档目录若位于同步目录内可能递归进入扫描；增加路径拓扑校验。
10. 批量运行多个云端 Profile 会各启一个 rclone daemon 且无上限；增加资源池和并发限制。

### P1

1. 进度总数只统计复制，不统计建目录和删除，完成视图与实际操作数不一致。
2. `ProgressWindow` 的速度/进度是文件计数模拟，不是字节进度。
3. 删除目录只删除空目录；版本策略对目录、远端以及部分失败的行为不统一。
4. `KeepDays` 从未生效，归档可能无限增长。
5. Profile 名称不能在主要工作流中编辑，导入时同 ID 的配置被静默跳过且无合并选择。
6. `Enabled` 有模型字段但 UI 缺少编辑和状态展示。
7. 过滤器使用简单表达式匹配完整相对路径，缺少规则语义说明与测试器，容易误配。
8. 端点字典构建未显式使用统一的大小写比较器；不同端点大小写语义需能力化。
9. 多个 `async void` 事件内存在分散异常处理；部分持久化异常可能进入 WPF 全局未处理异常。
10. 关闭时捕获所有异常并继续，可能造成 Profile/设置未保存而用户不知情。

## 7. 程序代码质量改进

### 7.1 架构拆分

`MainWindow.xaml.cs` 同时负责视图、配置、远端账号、rclone 生命周期、同步编排、批处理和日志，维护风险很高。建议采用 MVVM，并拆成：

- `MainWindowViewModel`：界面状态和命令；
- `ProfileEditorViewModel` / `SettingsViewModel`：配置编辑、验证、dirty tracking；
- `SyncOrchestrator`：扫描—规划—确认—执行—基线提交的唯一工作流；
- `EndpointFactory` / `RcloneHostPool`：端点创建与 daemon 生命周期；
- `SettingsStore` / `ProfileRepository`：版本化、原子化存储与迁移；
- `RunHistoryRepository`：运行、操作与错误历史；
- `SafetyValidator`：路径、删除阈值、空间、能力和计划过期验证。

本地和远端不应保留行为不同的两套执行器。抽象统一的事务阶段、验证、journal、版本管理和进度事件，只让端点适配器处理能力差异。

抽象层应遵循“已有重复、明确变化、安全边界、可测试 I/O”四项准入条件。除端点 provider 外，优先建立 `SyncOrchestrator`、统一执行管线、配置存储、凭据存储、端点能力以及结果/错误模型。同步模式、版本策略和安全校验只做轻量策略化。

近期不建设动态插件平台、事件总线、通用 `IRepository<T>`、运行时表单 schema 或每端点独立程序集，也不为只有一个实现的纯业务类机械增加接口。详细边界与落地顺序见 [抽象层审查](ARCHITECTURE_ABSTRACTION_REVIEW.md)。

### 7.2 类型和模型

- 使用强类型 `EndpointUri`，替代手工解析 `gdrive://` / `sftp://` 字符串。
- 为比较策略、自定义动作、错误策略、删除策略建立显式模型，避免枚举存在但未实现。
- 为操作结果建立 `Succeeded/Skipped/Failed/Cancelled`，不要仅以抛异常表示整个任务结果。
- 配置模型与运行时模型分离；运行时生成不可变快照，避免同步过程中 UI 修改对象。
- 引入端点能力协商，设置页按能力启用 hash、回收站、稳定 ID、空目录、服务器端移动等选项。

### 7.3 工程规范

- 将一行包含多个语句的代码格式化，启用 nullable、analyzers、editorconfig 和 warnings-as-errors（逐步导入）。
- 日志采用结构化事件和 correlation ID，禁止记录密码/token。
- 统一异常分类：用户输入、连接、认证、限流、磁盘空间、权限、冲突、内部错误。
- 所有长任务接受 `CancellationToken` 和进度事件；禁止用 UI 控件充当业务状态源。
- JSON 使用明确选项、schema version 和向后兼容测试。

### 7.4 测试策略

保留现有 planner/integration 测试，并新增：

- Profile/程序设置的序列化、迁移、损坏恢复、原子写入与并发写测试；
- 每种自定义动作组合、过滤器边界、大小写与时间精度测试；
- 删除阈值、空源保护、嵌套端点、归档目录递归、计划过期测试；
- 执行中取消、磁盘满、权限失败、源文件变化、目标被占用、断网/限流/认证过期测试；
- journal 崩溃恢复与基线只在成功后提交测试；
- rclone 使用 fake RC server 做契约测试，避免依赖真实云账号；
- ViewModel 单元测试和关键 WPF UI 自动化测试；
- 大规模目录（10 万/100 万项）性能和内存基准。

CI 至少执行 build、test、format/analyzer、打包 smoke test，并对发布产物验证 rclone、SQLite native DLL 和配置迁移。

## 8. 分阶段实施路线图

### 阶段 A：安全与配置基础（建议 2 个迭代）

- 拆分 `ApplicationSettings` 与 `SyncProfileSettings`，增加 schema/migration/validation。
- 建立 Profile 设置窗口 MVP：名称、端点、比较、同步、过滤、删除/版本、校验、并发。
- 禁用未完成的远端双向、Custom、RecycleBin；增加明确提示。
- 建立 `SyncOrchestrator`、统一结果模型和安全校验。
- 修复设置损坏提示、未保存切换、计划过期、删除阈值。

**验收**：用户能明确知道每个设置属于全局还是当前 Profile；重启后配置无损；任何可能大批删除的运行都有保护；UI 不再暴露未实现选项。

### 阶段 B：FreeFileSync 核心体验（建议 2～3 个迭代）

- 完成自定义同步动作矩阵、内容比较、过滤器编辑器、版本保留清理。
- 比较结果筛选/搜索/批量操作、真实字节进度、结构化日志和运行历史。
- 统一本地/远端执行器，远端 hash/重试/限流/认证错误处理。
- Profile 复制、分组、导入冲突处理、启停、最近状态。
- 建立端点 provider 注册体系，完成 S3 配置、凭据引用、能力探测与基础传输。

**验收**：典型本地备份、双向工作目录、镜像发布和过滤同步可完全通过 Profile 配置，无需手改 JSON；失败项可定位并重试。

### 阶段 C：自动化与远端可靠性（建议 2 个迭代）

- 实现远端持久基线后开放远端双向。
- 正式 CLI、Windows 计划任务向导、托盘和通知。
- 批处理并发治理、Profile 链、退出码与无人值守策略。
- 回收站、凭据管理、诊断包和配置全量导入导出。
- 内置 SFTP 服务器 MVP：单/多账号、密码与公钥认证、虚拟根目录、只读/读写权限、自动运行、托盘状态和审计日志。
- 完成 S3 分段上传恢复、版本控制感知、归档对象处理、成本提示和兼容服务预设。

**验收**：自动任务可无人值守运行，错误有确定退出码、日志和通知；断网、限流、重启后能够安全恢复或明确中止。

### 阶段 D：高级能力与产品化

- 移动检测、VSS/锁定文件、ACL/ADS、符号链接策略、限速。
- 国际化、无障碍、主题、高 DPI、安装器、自动更新与发布签名。
- 百万级条目性能优化和持续基准。

## 9. 建议的首批开发任务

按实际风险和依赖，首批可直接进入 issue tracker：

1. `P0 Settings split`：全局设置/Profile 设置分层及迁移。

8. `P1 Filter editor`：规则编辑、测试、预设、大小/日期条件。

## 11. 已移除功能

- **实时同步监控**（Issue #8）：`RealtimeMonitor`、`RealtimeRunCoordinator`、菜单“工具 → 实时监控…”以及 `RealtimeMonitorWindow` 已删除。当前 Profile 仅保留计划任务与手动触发两种执行方式；若后续需要文件变更驱动的同步，应作为新功能重新评估依赖与产品价值，避免再次引入未受控的实时触发循环。

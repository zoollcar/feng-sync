# Feng Sync — Agent Guide

## Purpose and scope

Feng Sync is a Windows desktop file-sync application. It synchronizes local folders and cloud endpoints — `sftp://`, `gdrive://`, `onedrive://`, `dropbox://`, `box://`, `webdav://`, and `s3://` — through bundled `rclone`. `EndpointSchemes` is the single map between those URI schemes, the rclone backend types, and `EndpointType`; add a provider there, never as another `StartsWith` in a caller. The WPF app, CLI, and scheduled runs share the same Core planning, safety, execution, history, and baseline code.

Use this file as a fast routing map. Inspect only the relevant subtree and its focused tests before editing; do not scan the whole repository unless the task genuinely crosses components.

## Environment and commands

- Target framework: .NET 10; Windows is required for WPF, Windows Task Scheduler, WMI mount discovery, and UI tests.
- Restore/build: `dotnet build .\FengSync.sln`
- Run desktop app: `dotnet run --project .\src\FengSync`
- Run core/CLI/integration tests: `dotnet test .\tests\FengSync.Tests\FengSync.Tests.csproj`
- Run WPF acceptance tests: `dotnet test .\tests\FengSync.UiTests\FengSync.UiTests.csproj`
- Core-only Windows gate: `pwsh -File .\scripts\Test-All.ps1 -Level Core`
- Full offline Windows suite: `pwsh -File .\scripts\Test-All.ps1 -Level UiOffline`
- Full offline suite, watching the scenarios run on screen: add `-ShowOnScreen` (off by default; see Testing and local artifacts)
- Online suite, including Google Drive: `pwsh -File .\scripts\Test-All.ps1 -Level Online`
- Release-package gate: `pwsh -File .\scripts\Test-ReleasePackage.ps1 ...` (all parameters are mandatory; see the script).

`Test-All.ps1` builds first, then runs Core/CLI/SFTP tests and UI tests. Do not run multiple UI suites concurrently: they manage desktop processes. Google Drive tests are external and credential-dependent; use `-Level UiOffline` for normal local verification and opt into them with `-Level Online`. A default `-Level UiOffline` run leaves the desktop and the pointer alone, so it is safe to start while you keep working; pass `-ShowOnScreen` when you want to watch it.

## Architecture and critical invariants

- Route normal comparisons/runs through `ProfileRunner`; it is the shared workflow for UI, CLI, and automation. Do not duplicate planning or bypass validation in a new entry point.
- A comparison captures a paired snapshot once. Planning, safety validation, freshness validation, and baseline commits must preserve that contract; avoid adding a broad re-scan to the execution path.
- `ThreeWayPlanner` uses the persisted paired baseline. A missing per-path baseline is first-sync behavior and must not propagate deletions. Unresolved conflicts must remain non-executable until the user resolves them.
- `SyncExecutorV2` is the sole executor; no legacy fallback exists. Preserve its bounded-channel/worker-pool concurrency, per-path freshness checks, temp-file atomic publish, copy verification option, journals, and cancellation behavior.
- Resume is Feng Sync's own behavior, never rclone's: rclone's copy path restarts an interrupted transfer from zero, `--inplace` and multi-thread `--inplace` both re-copy, and the RC API has no offset read or offset write. The engine therefore stages transfers at or above `EffectiveProfileSettings.ResumeMinimumBytes` (default 500 MB) under the deterministic `SyncInternalPaths.TransferTemporary(path)` name — `<name>.fengsync.partial` — and appends the missing tail itself. Preserve the three guards that must all pass before a staging file is continued: the recorded `TransferResumeState` (source size + modification time, in `TransferResumeStateStore`, deliberately in app data rather than beside the user's file), the 64 KiB seam comparison across the append point, and the size/threshold gate. A staging file that fails any guard is deleted, never appended to. The only offset read rclone exposes is `--rc-serve`, which is why `RcloneDaemon` starts it and why it must stay loopback-only behind the daemon's per-run credentials; `RcloneRcClient.OpenRangeAsync`/`ProbeAsync` are its only consumers. Continuation is only possible on the remote→local leg — an upload cannot be resumed and a remote→remote copy never touches local disk — so those paths discard their staging object and restart by design. Two further rules protect the append: a staging file whose seam does not match is *cut back* to the longest verified prefix (`VerifiedPrefixAsync`, bounded to a few write buffers) rather than deleted, because an interruption can tear the last write and losing a whole transfer over those bytes would defeat the feature; and `AppendRemoteAsync` takes that verified offset as a parameter and truncates the file to it before appending, so bytes that were never verified can never survive into the published file. Keep the resumable leg sequential: `--multi-thread-streams` writes chunks concurrently and can leave holes that a later run would wrongly trust as a prefix.
- A remote→remote cloud copy (`CloudTransferDirection.Copy`) is deliberately the one transfer that stages nothing: `EndpointTransfer.CopyServerSideAsync` hands rclone an `operations/copyfile` between two remotes, so this process never holds the bytes and has no seam to verify an append against, which means a cancelled or failed copy restarts the whole file and the transfer window says so (`HasCopyTasks`). Measured against the bundled v1.75.0: while the job runs the destination holds only rclone's own `<name>.<id>.partial` object, a stopped job leaves the destination directory empty, and a copy onto an existing object replaces it — so there is nothing to publish, nothing of ours to discard, and no cleanup needed before a retry. The destination is carried in `CloudTransferTask.TargetUri`/`TargetPath` (optional journal fields, appended last like `ErrorDetail` was), never in `LocalPath`, which every local-path consumer reads literally. Keep the refusal to run this call with a local endpoint on either side: writing straight to a destination name would bypass the temp-file-and-publish contract that makes a local write safe. `ServerSideCopyTests` pins the real-rclone behavior and `CloudTransferCopyTests` pins the payload with an injected fake RC client — the queue takes an optional client factory for exactly that reason.
- A cloud download stages under the file's **bare name**, not under its remote-relative path, so its source endpoint must be rooted at the file's own directory rather than at the endpoint root. `CloudTransferQueue.DownloadSourceUri` is that rule and the only thing standing between a nested download and a silently wrong file: measured at the wire against the bundled v1.75.0, a task whose `RemotePath` was `docs/a.txt` read `[nas:/]/team/a.txt` from an endpoint rooted at `team`, because the bare staging name resolved one directory up — a different object, and where one of that name exists it is fetched and published with no error at all. An upload needs no such adjustment (its source is already the local file's own directory and its destination carries the whole remote path), and a local URI is returned untouched because it has no root to compose against. `CloudDownloadSourceUriTests` pins the rule and `CloudDownloadPathFactTests` pins the landing with a real rclone and a decoy of the same name at the alias root.
- The browser's 复制 / 剪切 / 粘贴 (`RemoteEndpointManagerWindow`, rules in `CloudPastePlanner`) owes the user four properties. Only a **cut** may end in a delete, and only after its own queued copy has completed (`CloudTransferQueue.WaitForAsync`): a plain copy must send no `operations/deletefile` at all, and a failed or cancelled cut leaves the source where it was — reporting a duplicate as a success hides it. The transfer unit is one file, so a folder is listed as skipped rather than pasted. Each side is stripped against **its own** endpoint root exactly once (`CloudFileManagerService.RelativeToEndpoint`), because the browser addresses paths from the rclone remote root while the queue addresses them from `EndpointSchemes.BuildUri`'s root, and a paste between two endpoints with two different roots is where repeating one root silently writes to the wrong place. A cut inside one endpoint is `operations/movefile` — measured against the bundled v1.75.0 (`ServerSideCopyTests`): a same-endpoint server-side copy lands beside its source and keeps the source, a same-endpoint move lands at its destination and leaves no source — so it needs no delete and no confirmation, the same call 重命名 uses; a cross-endpoint cut confirms through `CloudDeleteSafety` (including the bulk second confirmation) before any byte moves.
- A cloud destination whose name is already taken is answered by `CloudConflictResolver`, never by a rule each call site re-derives. A saved `CloudUploadConflictPolicy` answers the whole batch through `ChoiceFor` — and `Ask` deliberately maps to `null`, because a setting that reads 每次询问 must not be implemented as the default answer — otherwise `AskFor` asks one name at a time and an 应用到全部 answer covers the rest. `Apply` returns **one placement per destination, in the input order**, a skip keeping its row and saying so, because an upload pairs its rows with the answers by position: two dropped folders can each hold one same-named file, and that pair addresses a single remote path, so a lookup by name would hand both rows the same rename and the second copy would replace the first. Rename candidates come from `CloudFileNames.KeepBothName` (`x.pdf` → `x (1).pdf`, compared case-insensitively, cut back to 255 characters so the backend accepts the name it is handed, bounded at 9999 attempts) and are checked against the *destination directory's* listing — a free name in one directory is not free in another. The question reaches the user through `CloudConflictPrompt`, a modal dialog, so the per-name loop is only testable through the window's `AskConflict` seam; and that seam's `null` **is** the user cancelling the batch, not "no seam installed" — a `??` fallback would open a dialog nobody can answer, and WPF refuses to give a dialog an owner that was never shown.
- The browser's 属性 reads the object itself through `operations/stat` (`RcloneRcClient.StatAsync` → `CloudFileManagerService.StatAsync`, with every row decided by the pure rules in `CloudItemDetails`) rather than trusting the row on screen, because a listing is a snapshot and cannot answer three of the panel's questions. All three are measured against the bundled v1.75.0 and pinned by `RcloneStatFactTests`: a **missing object answers `{"item": null}`, not an error** — so "the cloud no longer has this" is a value (`CloudItemStat.Missing`), and the panel must then show no size and offer no read; every object, directories included, answers a `MimeType` the listing never carries; and **no checksum is reported unless the call names it** in `opt.hashTypes` as an **array of hash names** — the numeric `opt.hashes` bit-field is silently ignored and `opt.HashTypes` fails to bind, so either mistake reads as "this backend has no checksums". Asking is not free: a 256 MiB local object answered in 154 ms unasked, 487 ms for md5, and 856 ms for md5+sha1+sha256, so opening 属性 never asks, the read lives behind the dialog's own 计算校验值 button, and only `CloudDetailsPanel.CanComputeHash` — not a row that happens to read 未计算 — decides whether that button appears. A folder's size stays 未统计 because nothing has counted its subtree; claiming a number there is the other thing this panel must not do. `operations/hashsum` does exist, but it takes **one** `hashType` string per call and answers a `"<hex>  <path>"` sum-file line, so asking for the whole chain that way is three round trips for less information than one stat already carries; `operations/hash`, `operations/checksum`, `operations/get` and `operations/geturl` are 404 in v1.75.0. The sync engine's own `RcloneEndpoint.StatAsync` (parent listing + `ReadPreferredHash`) stays as it was; `CloudItemDetails.HashPreference` is that same md5 → sha1 → sha256 chain so the browser and the engine never disagree about what a file's hash is.
- A folder's 大小 is counted by the cloud, never estimated locally, and 属性's own 统计大小 button is the only way to ask (`operations/size` through `RcloneRcClient.SizeAsync` → `CloudFileManagerService.SizeAsync`; wording and outcomes in `CloudFolderSize`, the offer rule in `CloudItemDetails.OffersSize`). Measured against the bundled v1.75.0 and pinned by `RcloneSizeFactTests`: **the directory rides inside `fs`** (`nas:team/docs`) because a `remote` field in this payload is **silently ignored** and the answer then covers the entire endpoint — the same ignored-key trap as `opt.hashes`, but this one hands back a plausible number instead of a missing one; `count` counts objects and never directories; an empty directory answers `{0, 0, 0}`, which is a real answer and not a failure, while a missing directory answers 404 `directory not found` and a file 500 `is a file not a directory`; `sizeless` stays its own field because a non-zero value means the byte total is a floor (rclone counts those objects as zero bytes), so `CloudFolderSize.TextFor` says how many were counted as zero. `max_depth` is honoured while `maxDepth`, `FastList` and `units` are ignored. Three rules hold it together: the walk **cannot be recalled** (measured — `job/stop` answers `{}` and the recursion keeps climbing, and `job/abort`, `core/commands` and `core/list` are 404), so a hint may only promise 不再等 and never that it stopped; a counted number is **never cached**, so a fresh panel reads 未统计 and offers the walk again rather than showing a total from an unknown moment; and a size walk issues no `operations/list`, so it must not record a 最近访问 visit — that is why counting lives beside a stat read and not in the browser's own path. A fourth rule follows from the first: `CloudDetailsPrompt` keeps **关闭 enabled** while the read runs (only the action button goes dark, so one click cannot send two walks), because a panel the user cannot leave would make the 不再等 wording a lie and would hold the whole manager window hostage to a call nobody can cancel. `CloudDetailsPanel.Action` carries **at most one** read per panel (a file may be hashed, a directory may be counted, never both, and an already-asked panel offers nothing), because each offer costs a whole pass over the cloud's bytes; and the offer stays on that one row rather than becoming a toolbar command — a walk over the whole selection would be one irrecoverable call per folder, and nothing here measures what that costs.
- 分享链接 is the one browser command that hands access to somebody else, so it is offered per file — never for a folder, never for a batch — and the cloud is asked only after the window's `ConfirmShare` agrees. Measured against the bundled v1.75.0 with a loopback `rclone serve s3` (`RclonePublicLinkFactTests`): a backend that has links answers `{"url": …}`; a backend without them answers HTTP 500 with "… doesn't support public links", which the shared `RcloneFailureClassifier` reads as a *temporarily broken connection*, so `CloudShareLinks.FromFailure` must test that wording **before** the category; and a directory or a gone object answers 404 "object not found", which is why folders are refused locally. The payload is exactly `fs` and `remote` because an unknown field is **silently ignored** rather than rejected, so a typo would ask for nothing and still look like a request; and no wording may promise an expiry or a revocation, because rclone's default is the least-restricted link it can make (readable with no account) while S3's is a presigned read that self-expires in about a week and ignores `unlink`. Keep the clipboard write behind `CopyLink`, and keep "generated but not stored" a distinct outcome from "no link" — the first tells the user to copy it themselves, the second tells them there is nothing to copy.
- 历史版本 is not a feature this application has, and the browser does not pretend otherwise. rclone exposes **no version list**, measured: `rc/list` registers 101 methods and the only one whose name mentions a version is `core/version`, which is rclone's own build number; `operations/versions`, `operations/history` and `backend/versions` all answer 404 `couldn't find method`; `operations/fsinfo` reports no versioning feature; and `operations/list`'s `opt` holds *listing* options rather than a backend-config override, so `--s3-versions` can only live in `rclone.conf`. That switch is deliberately left alone as well — it rewrites the namespace, so old versions arrive as objects and the file list fills with names that are not the objects the user has (GDrive has no such option at all, and OneDrive's and Jottacloud's `no_versions` are the opposite). `CloudVersionHistory` therefore names the trip rather than the feature: the row menu offers 在网页端查看历史版本… on **one file** (never a folder, never a batch), puts the reason on the item's own tooltip so it can be read before the click, and opens the provider's console from `CloudProviderDescriptor.WebConsoleUrl`. An endpoint with no single console — SFTP, WebDAV, and S3, whose console belongs to whichever compatible service it points at — has a `null` URL, and the browser then opens nothing and says where to look instead, because a wrong console is worse than an honest "there isn't one". Keep `OpenExternal` a seam: launching a browser is a machine-level effect, and the URL is the entire decision here since no cloud call is involved.
- Do not commit a new baseline after a failed run. Partial commits and recovery state are deliberate safety behavior.
- Endpoint operations must preserve `IEndpoint` capability and path-semantics differences. Treat remote endpoints as potentially case-sensitive and not necessarily able to enumerate empty directories.
- Destructive actions (deletes, overwrites, mirror/update plans, updater replacement) need explicit safety validation and focused regression tests. Keep user confirmation and delete thresholds intact.
- Credentials belong to rclone/app data, never profiles, CLI arguments, fixtures, logs, or source control. `FENGSYNC_DATA_DIR` is the supported isolated-data override for tests.
- An endpoint export carries only what is not a credential: name, type, provider, bucket/prefix, group, tags and the *names* of the rclone parameters. `CloudEndpointPortability`'s export records have no field for a value, and import treats the file as untrusted input — a remote name that could fabricate an `rclone.conf` section is refused. Preserve both properties when changing it.
- The updater has strict path and manifest validation. Retain path-containment checks, hashes, rollback behavior, and its prohibition on using a source checkout as an installation directory.
- Every shell (the main `App` and `DriveHubApp`) installs its services through `AppServices.Install` and implements `IAppServiceHost`. Shared windows and services must resolve dependencies from `AppServices` — never by casting `Application.Current` to a shell type — so any entry point can host them. `IAppServiceHost` deliberately excludes the SFTP server: two shells must not compete for one listen port.
- 局域网快传 (`src/FengSync.Lan/` + `Views/LanTransferWindow`) is the only entry point where this application listens on a network by itself; the bundled SFTP server is a different, loopback-oriented thing. Five properties are deliberate and must not be re-derived at a call site. The Kestrel host exists only while the window is open and is held by `App` **outside** `IAppServiceHost` — same fixed-port reason as the SFTP server, and `DriveHub` never shows it. A pairing token is a credential, so it goes only into the DPAPI blob `lan-peer-secrets.dat` and never into `lan-peers.json`, the QR, a log, a command line or a fixture; the QR prints the one-time code alone (single use, 120 s, and the phone page keeps the token in `sessionStorage`). Inbound bytes land through `SyncInternalPaths.TransferTemporary` staging and `LocalEndpoint`'s atomic publish, and a wire path that escapes the receive directory is **refused whole rather than renamed** — `CloudFolderDrag`'s stance. The write path needs a paired token and can reach nothing but the receive directory and this session's send basket, so there is no endpoint anywhere that takes a caller-built read path. And the transport is plain HTTP with **no request signing, on purpose**: an HMAC over a channel where the bearer token is already sniffable buys a false sense of safety, so the boundary sits instead in the single-use code, the human 同意 a stranger's first write requires, the revocable trust list, and that narrow authority. The service code therefore stays out of `FengSync.Core` as well: a `FrameworkReference Microsoft.AspNetCore.App` there would flow through the `ProjectReference` into the framework-dependent `FengSync.Cli` and make an installed ASP.NET Core shared framework a runtime prerequisite of a published exe.
- An S3 endpoint's prefix is enforced by an rclone `alias`, not by the UI: saving writes a hidden `<name>_s3` remote holding the credentials plus an `<name>` alias targeting `<backing>:<bucket>/<prefix>`. Consequences to preserve — the alias carries the user-facing name, so profiles and listings are unchanged; `CloudEndpointMetadata.RootPath` is therefore empty for an alias-backed endpoint (the alias root *is* the prefix, and repeating it would address the prefix twice) while `Prefix` keeps the value for display; `SelectEndpointRemotes` hides the backing store and surfaces no alias it did not create; deleting an endpoint must delete both remotes. S3 backends have no prefix option of their own (`rclone help backend s3`), so this pair is the only way to get a boundary rclone itself refuses to cross.
- Renaming an endpoint cannot go through rclone: there is no rename operation, and re-creating the remote with `config/create` is not a substitute — measured against the bundled v1.75.0, that call runs the backend's configuration state machine, so cloning an OAuth remote walks back into `oauth-confirm → oauth-islocal → oauth-authorize` and demands a fresh browser authorization instead of copying the stored token. `CloudEndpointRename` therefore rewrites the section in rclone.conf (`RcloneConfigFile`), which keeps every value byte-identical, and a running `rclone rcd` reads the change back on its very next call. Three rules hold that together: the rewrite is verified through the daemon before anything else changes (`config/get` must report the same parameters, and `config/listremotes` the new name and not the old one); rclone.conf, `cloud-endpoints.json`, `profiles.json` and `cloud-bookmarks.json` are backed up and restored together, because a config that still has the old section next to a profile that already points at the new name is worse than no rename — and a bookmark is one of those pointers: left naming a remote rclone no longer has, the jump list hides it, so the user's 收藏 looks emptied by a rename nobody mentioned. The bookmark rewrite runs **before** the profiles one, because reading `profiles.json` back is the step that can throw on input nobody controls (`ProfileStore.LoadAsync` has no recovery), and a rename that failed there must not leave the bookmarks moved while everything else stayed put; and an endpoint with a live mount is refused outright, since the mount holds the filesystem string `<name>:` that the daemon resolved when it mounted. An enforced-prefix S3 endpoint is two sections and both move, with the alias repointed at the renamed backing store.
- Mount lifecycle state (`RcloneMountService`'s managed set) is per process, not persisted, so each executable owns its own daemon and only stops the mounts it created. Each shipped entry point must therefore be published self-contained; WPF native dependencies do not flow through a `ProjectReference`.
- 收藏 and 最近访问 (`CloudBrowserBookmarks`, `CloudBrowserBookmarkStore`, `cloud-bookmarks.json`) are **two different promises** and must stay two rules: a favourite is something the user asked to keep, so its order is theirs, re-adding leaves it exactly where it was and nothing trims it; a recent visit is a queue the application wrote, so it is newest-first, one entry per place, capped at `RecentLimit` (20). The file holds place names only — an rclone remote name and a directory inside it — and `CloudBookmarkRecord` has no field that could carry a value, so it follows the same rule as an endpoint export. Four properties decide the wiring and all four are tested: a visit is recorded only **after** a listing arrives (a directory the cloud refused to list is remembered by the error in the status line, not as somewhere to jump back to); the `IsNewestVisit` gate is what stops every 刷新 from rewriting the file — proven by deleting the file, re-listing the same directory and showing it stays deleted; a jump adopts its endpoint through `SwitchEndpoint` and then lists the remembered directory **once**, because listing the root as well hands two answers to the file pane and whichever arrives last decides what the user is looking at; and entries whose endpoint the browser cannot offer are hidden, counted in the picker's ToolTip and never deleted, because rclone.conf can be unreadable for one refresh and a favourite the user chose should still be there when the endpoint comes back. An unreadable file is moved to a `.corrupt-<timestamp>.bak` on the window's read (the `SettingsStore` precedent) while a rename reads with `backUpUnreadable: false` — a rename must not put the user's file aside as a side effect. Two facts are worth knowing before changing the label: a bookmark stores the address the browser uses, so an endpoint rooted in `team` shows `nas · /team` and only a prefix-less endpoint shows `根目录`; and the row's *label* takes the endpoint's case from the list while its *bookmark* keeps the case it was written with, because rclone looks a section up case-insensitively. Every await taken while the store's gate is held must resume off the caller's context (`ConfigureAwait(false)`), measured directly: a listing that recorded its visit and returned before the write landed left the file locked for the whole process once that thread's dispatcher stopped pumping, and every later browser test then waited on a file nobody was writing (the harness watchdog cut each one at 90 seconds). `CloudEndpointMetadataStore`, `CloudEndpointRename` and `Filtering`'s per-path write locks have the same shape and were deliberately not changed here — fix one where a test can prove it. The window also keeps its **own in-memory copy** of both lists, so any code that rewrites the file behind it must re-read before anything else writes: `RenameEndpoint_Click` calls `LoadBookmarksAsync()` *before* `RefreshAsync()`, because that refresh starts a listing which records a visit, and a visit written from the stale lists moves the file straight back to the old remote name. That was measured, not inferred — 32 in-process bookmark tests and 18 rename tests stayed green while the desktop scenario failed to find the renamed favourite, because an action test cannot see a third representation. A second manager window already open in the same process still holds the same stale copy and is not covered by any test. Not proven, and deliberately not claimed: the corrupt-file sentence is observed through `BookmarkNotice` only — a window that is never shown does not reach `InitializeAsync`, which is where the status line is written after the endpoint count — and no case scrolls a capped list in the real shell.
- The browser's 回收站 is an application-owned folder `.fengsync-trash` filed at the **endpoint's** root, not rclone's trash: measured on the bundled v1.75.0 there is no trash verb at all (`operations/trash` → 404 "couldn't find method"), and the per-backend flags (`--drive-use-trash`) can neither be listed nor restored through the RC API, so a delete that leaned on the backend would have no 还原 to offer. An enforced-prefix S3 endpoint makes the endpoint root the only safe address — a path outside it is one the alias refuses. Files travel by `operations/movefile`, directories by `sync/move` (movefile refuses a directory outright), and four measured hazards decide the rules in `CloudRecycleBin`: both legs create the parents they need and **overwrite a destination file that already exists**, so landing names are chosen free from each destination directory's own listing (a name held by a *directory* is refused, so the listing is files *and* directories, not files only); a directory move onto an existing path merges and **leaves the source as an empty husk**, because `--delete-empty-src-dirs` clears the source's subdirectories but never its root, so the husk is removed with `operations/rmdir` whose existence is probed by `operations/stat` (`{"item": null}` for anything missing) rather than inferred from rmdir's answer — rmdir reports a missing path as an HTTP 500 in the operating system's own wording, which the shared classifier reads as a temporary failure. `operations/mkdir` is idempotent and creates parents, but refuses to replace a file that carries the folder's name, which is why 「回收站」 can create on the way in. `清空回收站` reuses `CloudDeleteSafety.Describe(..., insideRecycleBin: true)` with exactly one extra sentence: there must stay one delete threshold in the app, not a second one written for this button. That sentence follows **the view, not the control**: any delete asked for while the trash is on screen — 删除, Shift+Del, the row menu, 清空回收站 — passes the flag, because a row listed in a trash view is trash's own content whoever pointed at it.
- The file browser's keyboard (`CloudBrowserShortcuts.Resolve` → `RemoteEndpointManagerWindow.HandleKeyAsync`) is **routing, never rules**: one pure table turns a keystroke into one command (F5, Del → 移到回收站, Shift+Del / Ctrl+Del → 删除, F2, Ctrl+A/C/X/V) and every command dispatches to the method its toolbar button already calls (`BrowseAsync`, `RecycleSelectedAsync`, `DeleteSelectedAsync`, `RenameSelectedAsync`, `PasteAsync`, `SetClipboard`), so a shortcut can never grow a second, cheaper copy of a refusal, a confirmation or a threshold. Preserve three properties: the handler is attached to the **browser pane** and not to the window (the endpoint and mount lists keep their own keys); the typing gate runs after F5 and before everything else, because a TextBox consumes Del and Ctrl+A itself but **not** F2, so without the gate a half-typed address would open a rename question; and an unowned keystroke is left unhandled, or the list's type-to-select silently breaks. `PromptRename` is the seam for the rename question — a test must never be able to reach a real modal.
- The file browser has **one row collection and two drawings of it**. `RemoteEndpointManagerWindow` binds `FileList` to a single `_entries` list (`VisibleEntries`, after search and sort) that the keyboard, the clipboard, the trash and the delete threshold all read, so the grid view is `FileList.View = null` plus a different `ItemTemplate`/`ItemsPanel` — never a second `ObservableCollection` and never a second control, because two lists make `Ctrl+A` and the row menu disagree. Preserve that shape: toggling the view re-paints and re-aims the tile reads, sends **no** `operations/list`, keeps the same row objects (a test asserts `ReferenceEquals` per row) and keeps the selection across the `Items.Refresh()` that paints each arriving tile. The view choice persists in `ApplicationSettings.CloudBrowserView` (append-only enum, normalised before write-back) and is saved by the owning window as a read-modify-write of the loaded file — the same shape as `MainWindowSidebarWidth`, so it deliberately has no `SettingsWindow` entry; a row's picture is looked up through a window-scoped `CloudTileSourceConverter`, because a template cannot reach the store or the selected endpoint and a converter that *loaded* would network on every layout pass, on the UI thread, uncancellable. Two WPF facts decide how that swap is written, both measured against a shown window. A bound `GridView` writes **no** local `ItemTemplate`, `ItemsPanel` or `ItemContainerStyle` (all read `unset`) and draws its rows through the `ListView`'s own style, so restoring the list view means `ClearValue` on those properties: `ItemsPanel = null` is a *local null* rather than "unset", and it presents no row at all (cell text 2 → 0) while the collection keeps every item — an in-process assertion on `ItemTemplate`/`ItemsPanel` reading back `null` passes over that bug, which is why the toggle test asserts `DependencyProperty.UnsetValue` and the `sftp-ui` scenario toggles both ways and requires the row's `BoundingRectangle`. And a tile row's inner text never reaches UIA (the grid row is a `DataItem` with **zero** children, named by the item's `ToString()`), so `FileList.ItemContainerStyle` sets `AutomationProperties.Name="{Binding NameDisplay}"` — that is what makes a grid row reachable by name, and it also stops every row in either view announcing the whole record.
- Which rows may show a picture is `CloudBrowserTiles.DecideFor`, and it keeps five named states rather than one "no": the decodable set is **WPF's own built-in formats** (BMP, GIF, ICO, JPEG, PNG, TIFF) — `net10.0-windows` has no WinRT imaging, so WebP, AVIF, HEIC, SVG and RAW keep their file icon *with a sentence naming the format* instead of showing a broken picture. A tile is decoration the user never asked for, so it pulls at most 8 MiB, at 2 concurrent reads (the same number a user's own queued transfers get, and every tile travels through that same daemon), decodes at 64 px, and its bytes are cached by `AppDataPaths.CloudThumbnails` under a key carrying size and mtime (an overwritten picture must not keep painting old bytes) and trimmed past 64 MiB oldest-first. Rows the cache refused are remembered as refusals so one vanished file does not become a permanent stream of reads, and a cache file whose bytes will not decode is deleted only when this pull created it.
- 内置预览 (`CloudBrowserPreview` → `RemoteEndpointManagerWindow.PreviewAsync` → `CloudPreviewPrompt`) **refuses by default** and paints exactly two things: a WPF-decodable picture (≤32 MiB, decoded at 1024 px because the panel is 1000 px wide) and UTF-8/UTF-16 text (≤256 KiB). Everything else gets its own named state and its own sentence, never a blank panel: PDF/Office/archives/audio/video because this target framework ships no renderer for them (the existing download-then-external-open route stays, and 预览 is not even offered on such a row — a command that can only refuse is noise), a picture the listing already calls oversized is refused **before a read is spent**, bytes containing NUL are named binary whatever their extension claims, bytes that are not valid UTF-8 are refused rather than decoded with replacement characters (mojibake reads as file damage, and the app does not guess a code page it has no provider for), and picture bytes no decoder claims are called damaged. A preview is a read, not a cache: it must never touch the tile cache, which holds throwaway decoration and must not later be presented as the file itself.
- A WPF image decode failure does not arrive as one exception type, and a filter that names only the obvious ones lets the rest escape as a crash on the UI thread. Measured against the shipped toolkit: bytes no imaging component claims are a `NotSupportedException` ("No imaging component suitable"), an unrecognisable container is a `FileFormatException` (0x88982F07) which derives from `SystemException` and is therefore **not** caught by an `IOException` filter, and an incomplete stream is an `InvalidOperationException`. Both decode paths (`CloudThumbnailStore.Decode`, `CloudBrowserPreview.DecodePicture`) go through `CloudBrowserTiles.RefusesDecode` so they cannot drift apart.
- 拖出整个文件夹 (`CloudFolderDrag` → `RemoteEndpointManagerWindow.BeginFolderDragOutAsync`) hands Explorer a **whole mirror or nothing**. Explorer copies whatever is on disk at drop time and reports success either way, so a partial tree would be dropped as if it were the folder on screen; the window therefore starts a drag only when `CloudFolderDrag.IsMirrorReady` says every directory exists and every file is present at the length the cloud reported. The mirror comes from one recursive read (`CloudFileManagerService.ListTreeAsync`, whose shape is pinned by `RcloneRecursiveListFactTests`), and three rules follow from it: every directory the listing names is created before any transfer, because a recursive listing does report empty directories and no download would ever create one; a folder holding more than `MaxFilesPerDrag` files (the browser's own `SearchResultLimit`) is refused with a sentence telling the user to drag a subfolder, because one gesture means one journal row and one transfer per file; and a name the local filesystem cannot hold — `..`, a Windows-reserved character, or an S3 key pair rclone reports as both a file and a directory of one name — refuses the whole drag rather than rewriting it, since a renamed file inside a folder the user is about to trust is worse than no drag. A folder that needs more than one gesture keeps downloading and is revealed only when it is whole (`RevealFolderWhenReady`), the escape hatch a large single file already gets; and `CloudFolderDrag.IsReady` deliberately does **not** reuse `CloudDragCache.IsUsable`, because that gate distrusts an unknown size while a 0-byte cloud object is genuinely empty.
- The VFS cache that backs a mount is daemon-wide, and rclone resolves its cache root **once when the process starts**. The only working way to keep it inside app data is the `--cache-dir` flag on `rclone rcd` (see `RcloneDaemon.BuildArguments` and `AppDataPaths.MountCache`); the per-call `_config: { CacheDir }` override on `mount/mount` is silently accepted and ignored, so never reintroduce it as the mechanism. Two consequences follow: because the cache is shared, unmounting one mount must not delete it (a later mount of the same remote would re-download everything), and `RcloneDaemonArgumentsTests` asserts the flag is present precisely because a missing or misspelled flag fails silently.
- The cloud transfer queue's order and its rate limit are each one number with one reader, and neither may be re-derived at a call site. `CloudTransferTask.Order` is both the queue's order and the order the list shows: `AcquireSlotAsync` hands out slots in it, which is the only way 上移 / 下移 can mean "the order the user sees". A task added by hand must enter through `Start` rather than straight to `RunAsync`, because `Start` is what registers it in its batch — bypassing it left the task in no batch at all, so `BatchCompleted`, and with it the rate-limit hand-back and the 完成后动作, never fired for it (a real bug, fixed). The rate limit is `core/bwlimit`, and measured against the bundled v1.75.0 it is **global, not per-fs**: an `fs` parameter is accepted and ignored, a per-remote form (`nas:1M`) is refused with `bad bwlimit: bad suffix 's'`, and the `--bwlimit` time-table form answers a different error entirely (`need exactly 1 bandwidth setting`). The limit therefore belongs to the daemon rather than to a remote; the queue applies it when work starts and hands back `off` when the batch drains, and a queue that was never given a limit must push **nothing**, because `"off"` is still a write to the daemon and a default install never made one. `CloudTransferLimit.Rate` is the only formatter: every rate carries a `B` suffix (a bare number is not bytes — `512` means 512Ki and `1048576` means 1Gi), the two sides are `upload:download` in that order (`1M:100k` sets Tx 1MiB/s and Rx 100KiB/s), and `off` reads back as -1 on both sides.
- 「仅在此时间段传输」 is the queue parking itself, never a system-level scheduler: `CloudTransferTimeWindow` is half-open, wraps past midnight, and treats equal ends as the whole day, and a task that arrives outside the window waits while the queue's own one-shot wake-up is what starts it. Equal ends are deliberately **not** refused by `Parse` — a window nobody can enter is a configuration problem, and `ConfigurationValidator` is where that can be named, so `Parse` must not grow a second copy of the judgement. The parking is asserted through the window's own wording (`等待传输时段 22:00–06:00`), because that sentence is all the user sees of it.
- 清除已完成 archives before it removes anything. `CloudTransferHistoryRepository` is append-only, newest-first, capped, and reads a corrupt, empty or absent file as an empty history (the `RunHistoryRepository` precedent); it exists because the queue's journal drops a succeeded task's entry the moment it succeeds, so clearing the list used to leave no trace that the file was ever moved. 完成后动作 (`CloudPostTransferAction`) fires **only** for a batch in which everything succeeded and asks every time, because shutting a machine down after a batch that half failed would take away the only chance to look at what went wrong; it is owned by the transfer window rather than by the application precisely so the confirmation has somebody to answer it, and with no `Confirm` installed nothing happens at all — the alternatives are blocking forever and proceeding unasked. The shutdown prompt names `shutdown /a`, since a shutdown that can still be called off is a different proposition from one that cannot. 复制详情 / 查看日志 (`CloudTransferDiagnostics`, `CloudTransferRowMenu`) reuse what the queue already carries: the detail always starts by identifying the transfer, because a diagnostic with no subject cannot be attached to anything, and the log reader reports a missing or unreadable file **as** missing rather than as an empty log, because "there is nothing here" and "I could not look" are different answers.
- A mount's advanced options reach rclone as key names, and rclone **silently ignores** a name it cannot match to a field — no error, no warning, and the mount behaves like a default one. That is the entire reason this payload is pinned by tests rather than by reading the code. Measured against the bundled v1.75.0: a real key given an unreadable value is **refused** at JSON-decode time (`key "vfsOpt": Reshape failed to Unmarshal: …`, before any mount, so the fact needs neither WinFsp nor a mount point) while the *same* value under a typo'd key is accepted — which is what makes both "the name is real" and "a typo is silent" assertable in a gate with no mount driver. Names come from `options/info`'s own `FieldName` set and the two blocks are not interchangeable: `readOnly` is a **vfs** option (`ReadOnly`, not `ReadOnlyd`), `volumeName`/`networkMode` are **mount** options, and `umask`/`allowNonEmpty`/`allowOther`/`defaultPermissions` are documented "not supported on Windows" and are therefore never sent. `MountOptions.CreateVfsOptions` omits `CacheMaxSize` rather than writing a 0 when the ceiling is 0, because rclone's sentinel for "unspecified" is -1 and a literal 0 would report a zero-byte cache; a mount with no options at all must keep sending the historical payload unchanged. The poll-interval-outlives-dir-cache-time rule is a **warning**, not a refusal, because rclone accepts it and enforces nothing — inventing a refusal would claim an enforcement rclone does not have.
- Mount recovery is a list of records and a loop over them, and both are deliberately drivable without WinFsp. `MountRecordStore` persists `mounts.json` with `AutoMount` defaulting to **off** (auto-mounting slows start-up, WinFsp may not be installed and the network may not be up, and a silent failure is harder to diagnose than a prompt), carries **no credential field**, and merges `AutoMount`/`CreatedUtc` from any existing record on `RememberAsync` so a reconnect cannot silently drop the user's choice. Restore goes through `IMountStarter` rather than `RcloneMountService` so the part with decisions — what happens when one record fails — needs no driver. A mount's reported size comes from `operations/about` at mount time only and is **fixed at that moment** (a later quota change does not move it), and an endpoint that reports none gets the key omitted, never 0. 自动重连 is a prompt plus a button, never a silent background reconnect, and only for mounts this application created. The cache is daemon-wide (see the `--cache-dir` rule above): `MountCacheInspector` measures and clears it, and its containment check guards a sibling prefix so `cache` does not claim `cache-old`. A UNC target is accepted by rclone and comes back as the drive letter Windows allocated — measured `\\localhost\nonexistent-share-xyz\mnt` → `{"mountPoint": "Z:"}` — so `MountStatusLine.Describe` reports the point rclone **answered** with and names the requested one only as the thing that was not used; announcing the requested path would describe a mount point that does not exist.

## Change workflow

1. Start from the table above and read the relevant production file plus the closest existing test(s); use `rg` by symbol or behavior rather than broad file dumps.
2. Make the smallest cohesive change. Keep nullable reference types enabled and follow nearby C# style (file-scoped namespaces, concise records/classes, async APIs with `CancellationToken` where applicable).
3. Add or update tests in the corresponding suite. For a bug fix, prefer a regression test that demonstrates the original unsafe/incorrect behavior.
4. Run the narrowest affected test project first, then `dotnet build .\FengSync.sln`; run the full suite when changing shared synchronization, safety, configuration, packaging, or UI integration paths.
5. Before handoff, report tests actually run and preserve any unrelated working-tree edits.

## Testing and local artifacts

- UI/integration artifacts live in the ignored `.fengsync-test/` directory. Clear it once at the start of each test-suite run, then retain the current run's evidence until the next run; do not delete it during test teardown.
- `artifacts/` contains generated release packages and is ignored.
- Test fixtures are versioned in `tests/fixtures/`; never place real endpoints, tokens, passwords, private keys, or personal paths there.
- `ResumableDownloadTests` and `ConcurrentStagingReproTests` drive the real bundled `rclone.exe` — a local backend behind an `alias` remote, so bytes genuinely travel through the daemon's RC endpoint. They need no network and no credentials. Do not swap them for a fake client: the behavior under test is exactly what rclone does and does not support.
- Window behavior belongs in in-process tests, not in a desktop scenario: `CloudTransferWindowBehaviorTests`, `CloudTransferBehaviorTests`, `CloudFeatureBehaviorTests`, `CloudBrowserPasteTests`, `CloudBrowserGridViewTests`, `CloudBrowserPreviewTests`, `ResumeSettingsUiTests`, `S3PrefixBoundaryTests`, `DriveHubEntryPointTests` and the window cases in `UiFeatureBehaviorTests` build the real window on an STA thread (`RunSta`) with the shared theme dictionaries merged (`EnsureApplicationResources`) and drive it through `RaiseEvent`/the queue. They need no foreground session, run in milliseconds, and are the right place for "the buttons do what they say". `Invoke-UiScenario.ps1` scenarios are for what only the real shell can prove: reachability, UIA wiring, and AutomationIds. Three WPF limits shape that thread when the behavior under test is genuinely asynchronous (a queue worker posting its outcome back to the window): the process allows exactly **one** `Application`, and `Application.Current` is visible **only** on the thread that created it, so a helper may construct one only when none exists and must release it by closing its own dispatcher; the default `ShutdownMode.OnLastWindowClose` means a `window.Close()` ends that `Application` and every continuation still due, so an Application the test owns is set to `OnExplicitShutdown`; and a `Dispatcher.InvokeAsync` continuation only runs while its thread pumps, so the action runs inside `Dispatcher.PushFrame` with a watchdog that stops the frame rather than letting one hung window block the suite. A fourth limit decides *where* a rule lives: a modal dialog cannot be answered from an in-process test and `Window.Owner` throws for an owner that was never shown, so any decision a dialog asks for (`CloudConflictPrompt`'s per-name conflict answer, `TextPrompt`'s name and confirmation) is reached through a seam the test can supply — `AskConflict` on the window, and for the browser `SetBrowserViewAsync` / `PreviewAsync` / `BuildRowMenu`, which let a tile read or a preview refusal be asserted without a window ever appearing — while the dialog itself stays a thin shell over that decision. Code-built dialogs are outside the page-XAML scans, so they take their styles from the merged dictionaries through `TextPrompt.Resource<T>` rather than `StaticResource`. A fifth limit decides what a test about a *row* must do: a list in a window that is never shown is never measured, so its item template is never instantiated and none of its bindings are ever attached — and `RangeBase.Value` binds TwoWay by default, so a `ProgressBar` pointed at a read-only property passes every collection assertion and then throws `XamlParseException` out of the dispatcher when the first real row arrives, which kills the process mid-transfer (this happened twice, in `CloudTransferWindow` and then in `LanTransferWindow`, both from a `Percentage` bound without `Mode=OneWay`). A test that claims a row can be drawn must `Measure`/`Arrange`/`UpdateLayout` the list and read the control back out of the visual tree.
- Split a cloud transfer test by what it claims. **"What the queue sends rclone"** needs no daemon: `CloudTransferQueue` takes an optional RC-client factory, and `CloudTransferCopyTests` injects an `HttpMessageHandler` stand-in that answers `operations/copyfile` with a job id and then `job/status`/`core/stats` like v1.75.0 does — that is the only way to assert a payload's `dstRemote` or that a move/delete was *not* sent. **"Where the bytes actually land"** must run against the bundled `rclone.exe` behind an `alias` remote in `tests/FengSync.Tests` (`ServerSideCopyTests`, `ResumableDownloadTests`), because a fake only proves the fake.
- The `Invoke-UiScenario.ps1` scenarios run on a **private desktop by default**: the test host calls `CreateDesktop` and starts the scenario host on it through `CreateProcessW` with `STARTUPINFO.lpDesktop` (`PrivateDesktop.cs`), and every process the scenario starts in turn inherits that desktop. Windows on a desktop that is not being displayed are never composited to a monitor, and that desktop has its own input queue and its own foreground window — so the application opens real windows, raises them and takes the foreground without any of it reaching whoever is using the machine. Measured on this repository: 390 samples across a full scenario run saw zero application windows on the visible desktop and an unchanged foreground window. Do **not** reintroduce window parking (`-32000`, `SetWindowPos`, `ShowWindow`) or an application-side placement seam (`TestWindowPlacement`, `FENGSYNC_OFFSCREEN_WINDOWS`): a window moved after it has been shown has still been seen, it still activates, and it therefore still took the foreground — which is why parking never actually solved this. `-ShowOnScreen` (or `FENGSYNC_UI_SHOW_ON_SCREEN=1`, or `Test-All.ps1 -ShowOnScreen`) runs on the visible desktop instead, for watching a run by hand.
- Three **measured** limits shape that default path, and each one is a trap a later change falls into. **Synthesized pointer input cannot work on a private desktop**: with a control run of the same probe on both desktops, `GetCursorPos` and `mouse_event` fail with `ERROR_ACCESS_DENIED` and `SetCursorPos` returns false on the private one, while all three succeed on the visible one — so every pointer call stays behind `$script:showOnScreen`, and `PrivateDesktopHarnessTests` fails if one does not. **`Process.MainWindowHandle` stops naming the shell**: it is a heuristic (the first visible top-level window the process owns) and the application also owns the input-indicator overlays, which are created in-process a few seconds in and sit above everything — `ui-shell` failed with `Missing UI element: CompareButton` until the shell was resolved structurally, so use `Get-MainWindowHandle` and never `.MainWindowHandle` (the guardrail fails if it comes back). **A screen copy has no source**: `CopyFromScreen` throws "The handle is invalid" there, so `Capture-Element` renders the window with `PrintWindow` + `PW_RENDERFULLCONTENT` and the scenarios ask the application for software rendering, a supported production path; `ui-shell-native` keeps the native path deliberately and its manifest note records that its capture is the window frame only.
- Two WPF limits still explain why a step may need a keyboard or pattern equivalent: WPF hit-tests mouse messages against the position of the **real pointer**, so a posted click or drag is discarded and cannot be made to work without moving the cursor; and keyboard messages only reach WPF's input system when the window holds keyboard focus, which is why `Send-KeysToWindow` posts keys to the focused element rather than using `SendKeys`. `Find-AppWindow` and `Get-AppWindowHandles` enumerate top-level windows with Win32 `EnumWindows`, which sees the calling thread's own desktop — the harness runs on the same private desktop as the application, so that is exactly the application's windows. A scenario launches the `FengSync.exe` that sits in the **UiTests** output directory, so after editing the app build `tests/FengSync.UiTests` (or the solution) before trusting a scenario result — `dotnet build src/FengSync` alone leaves the copy stale and the scenario then passes over the very change it was meant to check.
- An in-process window test calls its harness in exactly one of two shapes, and the middle one is a bug: either the helper is synchronous (`static void RunSta(Action)`) and the test method is `void`, or the helper returns `Task` (`RunSta(Func<Task>)`, `WithWindow(...)`) and the test method is `async Task` that **awaits** it. A `Task`-returning harness reports its verdict *on that task* — its STA thread captures what the scenario threw and rethrows it from the task it hands back — so an un-awaited call still paints green while its assertions run after the test has returned, and its thread then overlaps the next test's, where a second WPF `Application` aborts the whole run. `UiTestAwaitGuardTests` scans `tests/FengSync.UiTests/*.cs` and fails on a call to a `Task`-returning harness whose statement neither awaits, returns, or forwards it.
- A `TextBlock` that displays live text (a status, a summary, a hint) must carry an `AutomationId` and **no** static `AutomationProperties.Name`. A static name replaces the text as the accessible name, so a screen reader announces the label instead of the content — and the desktop scenario can no longer read the value either. `LiveTextAccessibilityTests` scans the page XAML and fails on a regression; a self-binding `{Binding Text, RelativeSource={RelativeSource Self}}` (as `AboutWindow` uses) is the compliant way to name a block after its own text.
- Build outputs (`bin/`, `obj/`) and `.vs/` are generated files; do not edit or commit them.

## Release notes

- Every shipped executable declares its own version, so a release must bump all four together: `src/FengSync/FengSync.csproj` (main shell), `src/FengSync.DriveHub/FengSync.DriveHub.csproj` (cloud drive manager), `src/FengSync.Cli/FengSync.Cli.csproj` and `src/FengSync.Updater/FengSync.Updater.csproj`. Keep `Version`, `AssemblyVersion`, and `FileVersion` coherent, and keep the three-part number identical across the four — `ExecutableVersionTests` scans the csproj files and fails on a missing, mismatched, or unparsable version. `src/FengSync.Core` is a library and deliberately carries no version of its own.
- The release folder ships multiple entry points: `FengSync.exe` (main shell), `DriveHub.exe` (cloud drive manager) and `FengSync.Updater.exe`. DriveHub is published self-contained and only its four `DriveHub.*` files are copied into the publish folder, because the FengSync publish already provides everything else. `Test-ReleasePackage.ps1` requires `DriveHub.exe` and checks its `ProductVersion`; `DriveHubEntryPointTests` fails if the build stops emitting it.
- Generate `release-manifest.json` with `scripts/New-ReleaseManifest.ps1`; package naming, manifest contents, version, and checksum are verified by `Test-ReleasePackage.ps1`.
- `rclone.exe` is a committed, bundled runtime dependency. Replace it only deliberately and verify WPF, CLI, SFTP, mount behavior, and the `--rc-serve` range read that resume depends on (a `GET /[<fs>:]/<path>` with a `Range` header must answer `206` with a correct `Content-Range`).
